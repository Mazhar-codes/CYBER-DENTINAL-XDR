# Cyber Sentinel XDR — Project Analysis Report
**Date:** 2026-04-20  
**Analyst:** idps-project-analyst  
**Scope:** Full codebase review — Backend ML pipeline (rule_detector.py, hybrid_detector.py, collect_baseline.py, train_*.py), User Behavior model (xdr_runtime.py), React 19 + Vite frontend (NetworkDashboard, AlertsTable, NetworkMap, NetworkCard, api.ts)  
**Project Phase:** Active Development — Core ML pipeline partially implemented; FastAPI backend absent; two of four AI models not yet built

---

## Executive Summary

Cyber Sentinel XDR has strong foundational detection components: a production-quality rule detector, a well-designed hybrid ML network pipeline, and a user behavior model with validated performance metrics (F1: 0.92). The React 19 SOC dashboard renders correctly and is architecturally ready to receive data. However, the FastAPI backend (`backend.py`) — the central integration layer that calls every model, routes telemetry, manages MongoDB, and pushes alerts to the frontend — **does not exist anywhere in the repository**. Without it, no data flows between any component, and the system cannot function as an XDR. Two of four planned AI models are absent, the fusion engine is unimplemented, and three security vulnerabilities require immediate remediation.

**Overall project health score: 4.5 / 10** — strong parts, missing backbone.

## Layer-by-Layer Assessment

### Network Monitoring Layer

**Status: Partial**

Suricata provides flow data via `eve.json` with appropriate HOME_NET configuration. The `_open_with_retry()` helper in `rule_detector.py` correctly handles Windows file-locking contention when Suricata rotates its log. TShark is used in `collect_baseline.py` for PCAP capture, but the interface index is hardcoded to `-i 5` — a value that changes between machines and Windows updates, silently capturing the wrong interface or failing with no diagnostic.

The `Backend/ZEEK/` directory contains Zeek configs but they are never referenced by any Python or backend file. Zeek is dead code.

Flow micro-fragmentation is an acknowledged issue. The current mitigation (`max(duration, 1.0)` in `_parse_eve`) prevents division-by-zero but introduces systematic bias: a 0.1-second flow is reported as 1.0 second, suppressing rate spikes but also understating legitimate fast flows. A proper fix requires grouping micro-flows before feature extraction.

**Gaps:** No NetFlow/IPFIX, no PCAP forensic preservation, Zeek not integrated, interface hardcoded.

---

### ML Detection Pipeline

**Status: Partial — modules ready, integration absent**

**Stage 1 — Rule Detector (`rule_detector.py`)**

The rule detector is the most complete component in the repository. Six rules are implemented with per-source IP aggregation and rich `RuleHit` dataclasses carrying the statistics needed to populate the dashboard. The `HOST_SWEEP` rule correctly filters broadcast/multicast IPs. The `SYN_FLOOD` rule uses packet-weighted SYN/ACK counts (correct for volumetric analysis).

Noted weaknesses:
- `DATA_EXFIL` uses a static 50 MB threshold with no time-window normalization and no allowlist for known-safe destinations. A large Windows Update or OneDrive sync will trigger it.
- `rule_detector.py` is not imported or called from any file.

**Stage 2 — Hybrid ML Detector (`hybrid_detector.py`)**

The two-gate design is architecturally sound. Gate 1 (Personal IsolationForest) filters operator-normal traffic; Gate 2 (CIC RandomForest) classifies attack type across nine categories.

Critical issue: 12 of 62 CIC features are permanently hardcoded to `0.0` in `collect_baseline.py` because Suricata `eve.json` does not expose intra-flow packet-length variance or IAT standard deviation at the per-flow level. This affects: `Fwd/Bwd Packet Length Std`, `Flow IAT Std/Min`, `Fwd/Bwd IAT Std`, `Min Packet Length`, `Packet Length Std/Variance`, and the four `Idle/Active Std` features. Attack patterns that differ from benign primarily in packet-length variance (slow-rate DoS, C2 beaconing with jitter) will be systematically harder to detect.

**Stage 3 — User Behavior (`xdr_runtime.py`)**

The One-Class SVM achieves strong metrics per `retrain_corrected_answers_metrics.json` (Precision: 0.94, Recall: 0.90, F1: 0.92). Feature engineering extracts 14 behavioral signals from Windows event logs.

Critical issue: five OCEAN psychographic features (`O`, `C`, `E`, `A`, `N`) are hardcoded to `0.0` in every inference call, despite appearing as active features in the retraining metrics. The model runs with permanently zeroed dimensions it was trained on — this is silent capability degradation.

`xdr_runtime.py` is a standalone CLI. Its output is never merged into the fusion engine or displayed in the dashboard.

### Response Engine (SOAR-lite)

**Status: Not Implemented**

No command document writer, no endpoint agent polling loop, and no playbook execution exists anywhere. The `commands` and `endpoints` MongoDB collections have no writer or reader. The AlertsTable "Mark investigated" button calls `console.log()` only — it is a UI placeholder.

### Frontend / SOC Dashboard

**Status: Partially Implemented — UI functional, data flow broken**

The Vite + React 19 + TypeScript frontend is clean and correctly structured. Key observations:

- `NetworkDashboard.tsx` correctly maintains a 500-event rolling window with `useMemo` for stats.
- `NetworkMap.tsx` deduplicates links using a `Map` keyed on `src-dst`, meaning only the first connection between any IP pair is color-coded. Subsequent connections with different anomaly predictions are silently dropped from the graph.
- `AlertsTable.tsx` does not display SHAP explanations, attack type, severity, confidence, or rule name — all available in `RuleHit` but absent from the TypeScript interface.
- The `NetworkAnomaly` interface in `network.ts` contains fields the backend never computes (`ja3_rarity_score`, `tls_version`, `cipher_rarity`, `domain_entropy`) and is missing fields the backend does produce (`attack_type`, `severity`, `confidence`, `rule_name`, `gate_used`).
- `networkSocket.ts` subscribes to `"network_anomaly"` while `api.ts` subscribes to `"network"` — these are different event names. One client will never receive events. `networkSocket.ts` appears to be a superseded legacy file.
- `BACKEND_URL` is hardcoded to `http://127.0.0.1:8000`. Dashboard is non-functional in any non-localhost deployment.
- No authentication layer on frontend or backend.

## Security Vulnerabilities Found

### Critical

**1. No Authentication on Any API Endpoint (CWE-306)**

The backend does not yet exist, but there is no plan or scaffolding for authentication. When created, `/ingest`, `/commands`, and `/response` must require Bearer token or mTLS authentication. Without this, an attacker on the same network can inject false telemetry to poison models or directly trigger host isolation/process-kill SOAR actions.

- **Remediation:** Implement API key authentication via FastAPI `Depends()` before connecting any real endpoint agent. Generate per-host tokens at registration.

**2. PowerShell Command Injection in `get_service_status()` (`xdr_runtime.py`)**

```python
subprocess.run(["powershell", "-NoProfile", "-Command",
    f"(Get-Service {name}).Status"], ...)
```

The `name` parameter is interpolated without quoting or sanitization. Passing a name containing PowerShell metacharacters executes arbitrary commands.

- **CWE-78:** OS Command Injection
- **Remediation:** Use `psutil.win_service_get(name).status()` to eliminate subprocess entirely, or quote the parameter and validate input against `[A-Za-z0-9_-]`.

**3. `shell=True` Subprocess in `collect_baseline.py`**

```python
cmd = f'"{TSHARK_EXE}" -i {WIFI_INTERFACE} -a duration:{CAPTURE_SECONDS} -w "{pcap_path}"'
subprocess.run(cmd, shell=True, capture_output=True)
```

`WIFI_INTERFACE` is an unvalidated string routed through `cmd.exe`.

- **CWE-78 / CWE-88**
- **Remediation:** `subprocess.run([TSHARK_EXE, "-i", str(WIFI_INTERFACE), ...], shell=False)`

### High

**4. Hardcoded Absolute Paths Throughout Codebase**

Every Python file uses developer-specific hardcoded paths. The system silently degrades on any other machine.

- **Remediation:** Centralize all paths in `config.py` using `pydantic-settings` with `.env` file overrides.

**5. Insecure Deserialization via `pickle.load()` (`xdr_runtime.py`)**

```python
with path.open("rb") as f:
    return pickle.load(f)
```

Pickle files from untrusted sources execute arbitrary code on load.

- **CWE-502:** Deserialization of Untrusted Data
- **Remediation:** Use `joblib.load()` exclusively; verify SHA-256 checksums of model artifacts at startup; restrict ACLs on the model directory.

### Medium

**6. Reconnaissance Data in Browser Console (`api.ts`)**

```typescript
console.log("📡 Received network event:", data);
```

Raw IP addresses, prediction results, and Socket.IO payloads are logged on every event.

- **Remediation:** Gate all logging behind `import.meta.env.DEV`.

**7. CORS Policy Unknown / TLS Absent**

When the backend is created it must restrict CORS to the dashboard domain (not wildcard). All communication must use TLS (`wss://`, `https://`).

## Prioritized Implementation Roadmap

### Phase 1 — Critical Fixes (Immediate — this week)

1. **Create `backend.py` (FastAPI + Socket.IO)** — Highest priority. Minimum viable implementation:
   - FastAPI app with `python-socketio` as ASGI wrapper
   - `POST /ingest` with a Pydantic schema validating telemetry payloads
   - Instantiate `RuleDetector` and `HybridDetector` at startup
   - On each monitoring cycle: call rules → hybrid detector → emit via Socket.IO `"network"` event
   - pymongo client writing to `logs`, `predictions`, `alerts` collections

2. **Fix PowerShell injection in `get_service_status()`** — Replace f-string interpolation with `psutil.win_service_get(name).status()`.

3. **Replace `shell=True` in `collect_baseline.py`** — Rewrite both subprocess calls as list-form with `shell=False`.

4. **Remove debug console.log from `api.ts`** — Gate all payload logging behind `import.meta.env.DEV`.

5. **Delete `networkSocket.ts`** — Superseded by `api.ts`, wrong event name, potential memory leak.

---

### Phase 2 — Missing Components (Weeks 1–2)

6. **Integrate rule_detector.py into backend.py** — Wire the three-stage pipeline in order.

7. **Integrate xdr_runtime.py into backend.py** — Add `asyncio` background task calling `run_inference()` every 5 minutes. Emit via Socket.IO `"user_anomaly"` event.

8. **Implement Fusion Engine (`fusion_engine.py`)**
   ```python
   score = w_network * network_score + w_user * user_score + w_system * 0 + w_malware * 0
   ```
   Default weights: `w_network=0.40, w_user=0.35, w_system=0.15, w_malware=0.10`. Expose `POST /fusion`.

9. **Add API authentication** — Bearer token via FastAPI `Depends()` on `/ingest`, `/commands`, `/response`.

10. **Align `NetworkAnomaly` TypeScript interface** — Add `attack_type`, `severity`, `confidence`, `rule_name`, `gate_used`. Remove fields the backend doesn't compute.

11. **Centralize configuration** — Create `config.py` with `pydantic-settings`. Replace every hardcoded path.

12. **MongoDB write path** — Wire pymongo client into the detection cycle.

---

### Phase 3 — Hardening and Polish (Weeks 3–4)

13. **Implement SHAP explainability** — Add `shap.TreeExplainer` over `network_classifier.pkl`. Expose `GET /shap?alert_id=<id>`. Add expandable SHAP row to `AlertsTable.tsx`.

14. **Implement SOAR-lite Response Engine** — Write command documents to MongoDB `commands` collection on HIGH threat score. Implement endpoint agent polling loop.

15. **Fix TShark interface hardcoding** — Auto-discover via `tshark -D` or require mandatory env var with startup check.

16. **Fix OCEAN feature zeroing** — Either retrain excluding OCEAN features, or integrate a data source. Do not pass zeros for active model features.

17. **Fix 12 zeroed CIC features** — Use CICFlowMeter for Windows or retrain on the reduced feature set Suricata can actually provide.

18. **Frontend User Behavior panel** — Add dashboard section for user anomaly scores.

19. **Add TLS** — Configure uvicorn with SSL. Update `BACKEND_URL` to `wss://`/`https://`. Add CORS origin restriction.

20. **Model artifact integrity** — Store SHA-256 checksums at training time. Verify at load. Use `joblib.load()` exclusively.

---

### Phase 4 — Advanced Capabilities (Months 2–3)

21. **System LSTM Autoencoder** — Sequence model over CPU, memory, disk I/O, and Sysmon EventID 1 events. Train on 7–14 days of normal endpoint telemetry.

22. **Malware Random Forest (EMBER)** — Integrate EMBER 2018 dataset (2381 features). Expose `POST /predict/malware`.

23. **Alert correlation engine** — Temporal and spatial correlation: escalate when a host triggers multiple detection types within a configurable time window.

24. **Model drift detection** — Periodic KL-divergence check between current inference traffic and training baseline. Alert SOC when drift exceeds threshold.

25. **Zeek integration** — Connect `Backend/ZEEK/` configs to the pipeline. Parse `conn.log` and `dns.log` to compute `domain_entropy`, `dns_nxdomain_ratio`, and `periodicity_score`.

## Conclusion

The Cyber Sentinel XDR project has sound architectural vision and several well-implemented components. The immediate blocker is the absent `backend.py` — creating it with the three-stage detection pipeline wired together is the single highest-leverage action. Concurrently, three security vulnerabilities (command injection, shell=True, missing auth) must be patched before any real endpoint agents are connected. After Phase 1–2, the system will be functionally operational. Phases 3–4 bring it to production-grade.
